# 初期選定要素リスト

> 入力: 「社内イベント参加登録システム(拡張版) 課題仕様書」
> 既に決まっている制約(問いにしない): TypeScript / React / Express / Prisma / PostgreSQL、JWT 認証、bcrypt 等によるハッシュ化、`docker compose up -d` だけで DB・backend・frontend が起動すること、通知はログ出力レベルで可、初期ユーザーは seed で作成、既存のフルスタックテンプレート(npm workspaces モノレポ)を土台にする。

## 1. 全体アーキテクチャと技術スタック
### 選定・議論が必要なこと
- フロントエンドは SPA として API を叩く構成にするか、SSR を取り入れるか？（例: Vite + React SPA / React Router のフレームワークモード / Next.js）
- フロントのサーバー状態(イベント一覧・空き数など)をどう管理するか？（例: TanStack Query / SWR / Redux Toolkit Query / useState + useEffect）
- 入力バリデーションのルールをフロントとバックでどう共有するか？（例: 共有パッケージの Zod スキーマ / OpenAPI から生成 / 各側で個別実装）
- 空き数・待機順位など頻繁に変わる値をリアルタイムに反映するか？（例: 画面表示時に取得のみ / ポーリング / WebSocket・SSE）
- 日時処理に使うライブラリをどうするか？（UTC 保存・JST 表示の要件より）（例: 標準 Date + Intl / date-fns(-tz) / Day.js / Temporal polyfill）
- UI のスタイリング手段とコンポーネントライブラリを使うか？（例: Tailwind CSS のみ / shadcn/ui / MUI / CSS Modules）
- テストフレームワークをどう揃えるか？（例: Vitest + Supertest + Testing Library / Jest / Playwright を E2E に追加するか否か）

## 2. コード管理とディレクトリ構成
### 選定・議論が必要なこと
- リポジトリ構成をどうするか？（例: npm workspaces のモノレポ(frontend / backend / shared) / フロント・バック別リポジトリ / pnpm・Turborepo）
- Prisma スキーマとマイグレーションをどこに置くか？（提出物に `prisma/schema.prisma` の指定あり）（例: ルート直下の `prisma/` / `backend/prisma/` / shared パッケージ）
- バックエンドのレイヤー分けをどうするか？（例: routes → controllers → services → Prisma の 3 層 / ドメイン単位のモジュール / Clean Architecture 風に repository 層を追加）
- フロントエンドのフォルダを機能単位にするか種類単位にするか？（例: `features/events` などの機能単位 / `components` `hooks` `pages` の種類単位 / 画面単位）
- 「キャンセル待ち」「出席」「フィードバック」をイベント機能の一部にするか、独立した機能モジュールにするか？（例: events に同居 / registrations・feedbacks を別モジュール / 1 つの大きな event モジュール）
- 権限判定ロジックをどこに集約するか？（仕様のヒント「各 API で個別に書くと漏れる」より）（例: ルート単位のミドルウェア / サービス層のポリシー関数 / デコレータ・ガード）
- ブランチ運用とコミットメッセージ規約をどうするか？（例: main 直コミット / feature ブランチ + PR / Conventional Commits を採用するか）
- テンプレートに含まれるサンプル機能(Todo・サインアップ)をどう扱うか？（例: 削除する / 残して参考にする / 別ブランチに退避）

## 3. セキュリティ・認証・認可
### 選定・議論が必要なこと
- JWT をクライアントのどこに保持するか？（例: httpOnly Cookie / localStorage + Authorization ヘッダ / メモリ + リフレッシュトークン）
- トークンの有効期限と期限切れ時の扱いをどうするか？（例: 長めの単一トークン / 短命アクセストークン + リフレッシュトークン / 期限切れでログイン画面へ）
- ロールがトークンに入っている以上、ロール変更をいつ反映させるか？（例: 次回ログインまで反映しない / リクエストごとに DB で再確認 / トークン失効リスト）
- 「主催者」権限をどう判定するか？（独立ロールにしない仕様より）（例: リクエストごとにイベントの作成者 ID と比較 / トークンに主催イベント ID を含める / 共同主催者テーブルを設ける）
- サインアップ機能を残すか？（例: 削除して seed のみ / admin 用のユーザー作成画面を作る / 残す）
- ログインの総当たり対策をするか？（例: IP 単位のレート制限 / アカウントロック / 対策なし）
- XSS・SQL インジェクション対策の方針をどうするか？（イベント説明文・レビューコメントの自由入力より）（例: React のエスケープ + 生 HTML 禁止 / Markdown 対応してサニタイズ / ORM のみ使用し生 SQL 禁止）
- CSRF 対策をどうするか？（Cookie 認証を選んだ場合）（例: SameSite=Lax / CSRF トークン / カスタムヘッダ必須）

## 4. データ管理と主要なビジネスルール
### 選定・議論が必要なこと
- イベント削除を物理削除と論理削除のどちらにするか？（例: 物理削除 + カスケード / 論理削除(deleted_at) / ステータスで「中止」扱い）
- 主催者を参加者として扱うか？（例: 自動で参加確定にして定員に含める / 参加者とは別管理で定員に含めない / 主催者も任意で登録可）
- カテゴリ削除時に紐づくイベントがある場合どうするか？（例: 削除拒否 / 論理削除(無効化) / 「その他」など別カテゴリへ移動）
- タグの正規化をどこまでするか？（例: 入力そのまま / 前後空白除去 + 小文字化 / 全角半角統一(NFKC)まで / 1 イベントあたりの上限数）
- 参加確定とキャンセル待ちを同じテーブルで状態管理するか、別テーブルにするか？（例: registrations に status 列 / registrations と waitlist の 2 テーブル）
- キャンセル待ちの順番(position)を、待機解除時にどう整合させるか？（例: 後続を詰めて振り直す / 番号は振り直さず順序だけ保つ / 登録日時で順序を決める）
- 同時に複数キャンセルが起きた場合の繰り上げの排他制御をどうするか？（例: イベント行の SELECT ... FOR UPDATE / シリアライザブル分離レベル + リトライ / 楽観ロック(version 列)）
- キャンセル済みの参加登録を記録として残すか？（例: 行を物理削除 / status=CANCELLED で残す / 別の履歴テーブルへ）
- 繰り上げはいつまで行うか？（例: 開催開始まで / 登録締切まで / キャンセル期限まで）
- 定員を編集で増減した場合、既存参加者・待機者をどうするか？（例: 現在の参加者数未満への減少は禁止 / 超過分を待機に戻す / 増えた分を自動繰り上げするか否か）
- 「開催前まで」がデフォルトの締切・期限を、開始日時と終了日時のどちらで判定するか、終了日時を持つか？（例: 開始日時のみ持つ / 開始・終了の両方を持つ / 開始日時 + 所要時間）
- 開催日時変更の「警告」をどう実現するか？（例: サーバーログ出力のみ / API レスポンスに警告を含めて画面表示 / イベントに「日時変更あり」ステータスを持たせる）
- 開催開始後のイベント編集をどこまで許可するか？（例: すべて不可 / 日時・定員以外は可 / すべて可）
- 「累計参加数」に何を数えるか？（例: 出席マーク済みのみ / 開催済みで欠席以外 / 参加登録した全件）
- 出席マークを「未マーク」に戻せるようにするか？（誤操作リカバリより）（例: 出席⇔欠席の切替のみ / 未マークへの戻しも可）
- フィードバック投稿後に出席状態が「欠席」に修正された場合、既存レビューをどう扱うか？（例: そのまま残す / 自動で非公開 / 削除）
- 非公開化されたレビューを投稿者本人に見せるか？（例: 見せない / 「非公開」表示付きで見せる / 本人には通常どおり見せる）
- 日時の保存形式をどうするか？（例: timestamptz で UTC / timestamp(タイムゾーンなし)で UTC / 文字列）

## 5. 通知システム
### 選定・議論が必要なこと
- 通知の対象イベントをどこまで定義しておくか？（例: 繰り上げのみ / 繰り上げ + 日時変更 + イベント削除 / なし）
- 「ログ出力」の形式をどうするか？（例: console 出力 / 構造化ログ(pino 等)で JSON 出力 / DB の通知テーブルに書き込み）
- 将来の通知機能に向けて、繰り上げ履歴以外にも記録を残すか？（例: 繰り上げ履歴テーブルのみ / 汎用の通知・アクティビティテーブル / 残さない）
- 通知処理を本処理と同期で行うか？（例: トランザクション内で同期 / コミット後に実行 / キュー経由で非同期）
- アプリ内通知(画面上のお知らせ)を作るか？（例: 作らない / 詳細画面のバナーのみ / 通知一覧画面を作る）

## 6. API設計と認可方針
### 選定・議論が必要なこと
- API のスタイルをどうするか？（例: REST / GraphQL / tRPC）
- 「自分の参加登録」の URL をどう表すか？（例: `/events/:id/registration`(単数・ログインユーザー) / `/events/:id/registrations/:userId` / `/registrations` に eventId を渡す）
- 参加登録とキャンセル待ち登録を 1 つの API にまとめるか分けるか？（例: 登録 API が満席時に自動で待機登録 / 別エンドポイント / 種別をボディで指定）
- レスポンスとエラーの形式をどう統一するか？（例: `{ data }` / `{ error: { code, message } }` の封筒形式 / RFC 7807 Problem Details / ステータスコードのみ）
- ビジネスルール違反(満席・締切後など)に返すステータスコードをどうするか？（例: 409 Conflict / 422 Unprocessable Entity / 400 に統一）
- 他人のイベントを編集しようとした場合や、存在しないリソースのステータスをどうするか？（例: 403 / 404 で存在を隠す）
- 一覧 API の検索・ページング方式をどうするか？（例: offset/limit / page/limit / カーソル方式、ソート指定の書式）
- 画面のボタン制御に必要な権限情報をどう渡すか？（例: 詳細 API に `permissions` を含める / フロントでロールと ID から判定 / 別 API）
- 匿名レビューの投稿者情報を admin にだけ返す仕組みをどうするか？（例: 同じ API で閲覧者のロールにより出し分け / admin 専用 API を分ける）
- admin 専用操作の URL をどう分けるか？（例: `/admin/...` 配下にまとめる / 通常リソースに置いて権限で制御）

## 7. 画面構成とUI/UX
### 選定・議論が必要なこと
- 画面遷移の単位をどうするか？（例: 作成・編集・出席管理・フィードバックを個別ページ / モーダル中心 / 詳細画面内のタブ）
- 参加登録ボタンの状態(登録 / キャンセル待ち / キャンセル / 受付終了 / 主催者)をどう出し分けるか？（例: 1 つのボタンを状態で切替 / 状態ごとに別ボタン + 説明文）
- キャンセルや削除など取り消せない操作の確認方法をどうするか？（例: 確認ダイアログ / 取り消し可能なトースト / 確認なし）
- イベント一覧の表示形式と、デフォルトで過去イベントを表示するか？（例: カード / テーブル、未来のみ / 全件 / 切替トグル）
- タグ検索の UI をどうするか？（例: 自由入力 / 候補のオートコンプリート / タグクリックで絞り込み）
- 日時入力の UI をどうするか？（例: ネイティブ `datetime-local` / 日付ピッカーライブラリ / 日付と時刻を別入力）
- マイページの統計(出席率・カテゴリ別傾向)をどう見せるか？（例: 数値のみ / 表 / グラフライブラリでチャート化）
- 権限のない画面に直接アクセスした場合の挙動をどうするか？（例: 一覧へリダイレクト / 403 画面 / 404 画面）
- 画面を開いている間に満席・締切などの状態が変わった場合の扱いをどうするか？（例: エラー表示のみ / エラー表示 + 自動再取得 / 定期更新）

## 8. インフラと開発環境
### 選定・議論が必要なこと
- Docker コンテナでフロント・バックをどの形態で動かすか？（例: 開発サーバー(ホットリロード)+ ボリュームマウント / ビルド済み本番イメージ / フロントは nginx 配信）
- コンテナ起動時にマイグレーションと seed をどう実行するか？（例: backend のエントリポイントで自動実行 / 別の一回限りのコンテナ / 手動コマンド）
- seed のイベント日時をどう用意するか？（過去日作成禁止・出席は開催後のみ、の確認のため）（例: 起動時刻からの相対日時 / 固定日時 / 状態別に複数パターン）
- テスト用 DB をどう用意するか？（例: 同じコンテナ内の別 DB / テスト専用コンテナ / Testcontainers）
- 環境変数と秘密情報の管理をどうするか？（例: `.env` + `.env.example` / compose に開発用の値を直書き / Docker secrets）
- ホストとコンテナで `node_modules` をどう扱うか？（例: 名前付きボリュームでコンテナ専用 / ホストと共有 / イメージ内に焼き込み）
- CI を用意するか？（例: GitHub Actions で lint・型チェック・テスト / なし）
- 動作確認の成果物(スクリーンショット・デモ動画)をどう残すか？（例: `docs/screenshots/` に保存 / Playwright のスクリーンショット・動画機能 / 手動録画）
