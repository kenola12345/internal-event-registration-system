# 詳細要求リスト

> Manifest Phase 3 の成果物。出典: 課題仕様書(以下「仕様」)、`docs/技術スタック.md`(Phase 2)、`docs/manifest.md` の設計判断(ユーザーが採用を決定)。網羅確認: `docs/初期選定要素リスト.md`。

## 1. アーキテクチャ・技術スタック

### 全体
- 構成は SPA + REST API とし、SSR は採用しない。
- 既存テンプレート(npm workspaces のモノレポ)を土台にする。
- フロントとバックの入力バリデーションは `shared/` の Zod スキーマを共有する。
- 空き数・待機順位などのリアルタイム反映は行わない。表示時に取得し、操作後に再取得する。

### フロントエンド
- React 19.3 + Vite 8(SPA)
- React Router 8(ライブラリモード)
- TanStack Query 5(サーバー状態の管理)
- Tailwind CSS 4.3(コンポーネントライブラリは使わない)
- Zod 4.6
- date-fns 4 + date-fns-tz 3

### バックエンド
- Node.js 24 + Express 5.3(ESM, TypeScript)
- Zod 4.6
- Prisma 7.10(`@prisma/adapter-pg`)
- jsonwebtoken 9、bcrypt 6、cookie-parser、helmet、express-rate-limit
- ログは既存の JSON Lines ロガー(`lib/logger.ts`)を使う。

### データベース
- PostgreSQL 17(Docker)
- マイグレーションは Prisma Migrate。

### テスト
- ユニット / API / コンポーネントテストは Vitest 5。
- API テストは Supertest 7 で実 DB(`app_test`)に対して実行し、Prisma をモックしない。
- コンポーネントテストは Testing Library 16。
- E2E テストは Playwright(`@playwright/test`)、対象ブラウザは Chromium のみ。

## 2. セキュリティ・認証・認可

### 認証
- ログインはメールアドレス + パスワード。(仕様)
- セッションは JWT で管理し、トークンにロールを含める。(仕様)
- JWT のペイロードは `sub`(ユーザーID)と `role` のみとする。
- JWT の署名アルゴリズムは HS256 に固定する。
- JWT は httpOnly Cookie(`token`, `SameSite=Lax`, 本番は `Secure`)に保持する。
- JWT の有効期限は 7 日の単一トークンとし、リフレッシュトークンは使わない。
- トークン期限切れ(401)の場合は `/login` に遷移し、再ログイン後に元のページへ戻す。
- `requireAuth` はリクエストごとに DB からユーザーの現在のロールを読み込む。ロール変更は即時に反映され、存在しないユーザーのトークンは拒否する。
- ログアウトは Cookie を削除する。未ログインで呼んでも成功(204)とする。
- ユーザーは seed で作成する。サインアップ API・画面は削除する。
- パスワードは bcrypt(12 ラウンド)でハッシュ化して保存する。平文保存は禁止。(仕様)
- ログイン失敗時は、メール不存在とパスワード誤りを区別しないメッセージを返す。
- ログインは IP 単位でレート制限する。
- 未ログインで保護ページにアクセスした場合は `/login` にリダイレクトし、ログイン後に元のページへ戻す。

### ロール
- ロールは `MEMBER` と `ADMIN` の 2 つ。テンプレートの `USER` は `MEMBER` にリネームする。
- 「主催者」は独立したロールにしない。イベントの `organizerId` がログインユーザーと一致する場合に、そのイベントに対してのみ主催者権限を持つ。(仕様)
- 主催者権限はトークンに入れず、リクエストごとに DB のイベントから判定する。
- admin が自分でイベントを作成した場合も主催者ルールが適用される。

### 認可
- 未ログインで呼べる API は `POST /api/auth/login` と `GET /api/health` のみ。他の全ルートに `requireAuth` を付ける。
- admin 専用ルート(カテゴリ管理、レビュー非公開化、強制キャンセル)は `requireRole("ADMIN")` を付ける。
- イベント単位の権限(主催者 or admin)は `services/policies/event-policy.ts` に集約し、各サービスは必ずこれを通す。
- 他人のイベントを編集・削除しようとした場合は 403 を返す(イベントは全員に公開されているため)。
- 論理削除済みイベントは誰に対しても 404 を返す。

### 権限マトリクス
- 全ロール: ログイン、イベント一覧・詳細の閲覧、イベント作成ができる。(仕様)
- イベント編集・削除: 主催者は自分のイベントのみ、admin は全イベントで可能。参加者としての member は不可。(仕様)
- 参加者一覧(出席状況・待機リスト込み)の閲覧は主催者(自分のイベント)と admin のみ。それ以外は参加者の氏名のみ閲覧できる。
- 参加登録・キャンセル・キャンセル待ちは、自分が主催するイベント以外で member・admin とも可能。(仕様)
- 他人の参加の強制キャンセル(期限後も可)は admin のみ。
- 出席マークは主催者(自分のイベント)と admin のみ。(仕様)
- フィードバック投稿は、自分が主催するイベント以外で条件を満たす member・admin が可能。(仕様)
- 匿名レビューの投稿者閲覧、非公開レビューの閲覧は admin のみ。
- カテゴリマスタ管理と不適切レビューの非公開化は admin のみ。(仕様)

### その他のセキュリティ
- SQL は Prisma のクエリビルダか `$queryRaw` タグ付きテンプレート(パラメータ化)のみ使い、文字列連結の SQL を書かない。
- `dangerouslySetInnerHTML` を使わない。説明文の改行は `white-space: pre-wrap` で表示する。
- パスワード・トークン・Cookie・リクエストボディをログに出さない。
- イベント作成時の `organizerId` はボディから受け取らず、ログインユーザーを使う。

## 3. データモデル

- ID は cuid 文字列。
- 日時カラムはすべて `timestamptz`(`@db.Timestamptz(3)`)で UTC 保存する。
- 既存の `users` テーブルはテンプレートの列名(camelCase)を維持し、型は timestamp から timestamptz に変更する。新規テーブルは snake_case(`@map`)にする。
- テンプレートの `Todo` モデルは削除する。
- enum: `UserRole`(`MEMBER` / `ADMIN`)、`AttendanceStatus`(`UNMARKED` / `PRESENT` / `ABSENT`)、`PromotionTrigger`(`CANCELLATION` / `ADMIN_CANCELLATION` / `CAPACITY_INCREASE`)。
- テーブル: `users`, `categories`, `events`, `tags`, `event_tags`, `registrations`, `waitlist_entries`, `waitlist_promotions`, `feedbacks`。
- カテゴリとイベントは 1 対多(`events.category_id` 必須)。
- タグとイベントは多対多で、中間テーブル `event_tags`(複合 PK `(event_id, tag_id)` + `(tag_id)` インデックス)で実装する。(仕様)
- 参加確定(`registrations`)とキャンセル待ち(`waitlist_entries`)は別テーブルにする。
- 一意制約: `registrations (event_id, user_id)`、`waitlist_entries (event_id, user_id)`、`waitlist_entries (event_id, position)`、`feedbacks (event_id, user_id)`、`categories.name`、`tags.name`、`users.email`。
- `events.category_id` は `ON DELETE RESTRICT`。
- イベントは `ends_at`(開催終了)を必須で持つ。
- イベントは `location`(任意、100 文字以内)を持つ。
- イベントは `schedule_changed_at`(参加者がいる状態で日時を変更した最終時刻)を持つ。
- 出席マーク時は `attendance_marked_at` と `attendance_marked_by_id` を記録する。
- フィードバックの非公開化時は `is_hidden`, `hidden_at`, `hidden_by_id` を記録する。
- 匿名投稿でも `feedbacks.user_id` は保存する。
- CHECK 制約(マイグレーション SQL に追記): 定員 `1..1000`、`ends_at > starts_at`、締切・期限は NULL または `<= starts_at`、`position > 0`、評価 `1..5`。
- CHECK 制約は `--create-only` で生成したマイグレーションに、適用前に追記する。適用済みマイグレーションは編集しない。

## 4. データ管理・ビジネスルール

### 日時と期限
- 登録締切の実効値は `registration_deadline ?? starts_at`。(仕様: 未設定なら開催前まで)
- キャンセル期限の実効値は `cancel_deadline ?? starts_at`。(仕様: 未設定なら開催前まで)
- キャンセル期限は `starts_at` 以前であれば過去の日時も設定できる(登録締切と違い「現在より未来」の制約は設けない)。(Phase 5 で決定)
- 締切・期限を設定する場合は `starts_at` 以前でなければならない。
- 判定に使う現在時刻はサーバー時刻のみ。

### イベント
- 過去日時のイベントは作成できない(バリデーションエラー)。(仕様)
- 登録締切を設定する場合は現在より未来でなければならない。
- イベントの入力制約: タイトル 1〜100 文字、説明 1〜2000 文字、場所 0〜100 文字、定員 1〜1000、タグ 0〜10 個。
- 無効化されたカテゴリは新規作成・編集で選択できない。
- 削除は論理削除(`deleted_at`)とする。理由: 参加登録・繰り上げ履歴・フィードバックの履歴を残し、誤削除時に DB から復旧できるようにするため。
- 論理削除済みイベントは一覧・詳細・マイページ・集計から除外する。
- イベント削除時に参加確定者・待機者がいれば件数をログ出力する。
- 削除したイベントの復元 API は作らない。
- イベントは開催前・開催中・開催済みのいずれの状態でも削除できる(admin が開催済みの不適切なイベントも削除できるようにするため)。(Phase 5 で決定)

### イベントの編集
- 日時(`starts_at` / `ends_at`)を変更する場合、新しい `starts_at` は未来でなければならない。
- 参加確定者がいる状態で日時を変更した場合: 警告ログを出力し、`schedule_changed_at` を記録し、API レスポンスに `SCHEDULE_CHANGED_WITH_PARTICIPANTS` の警告を含める。(仕様: 警告を出す)
- 開催開始後は、日時・定員・締切・期限を変更できない。タイトル・説明・場所・カテゴリ・タグは変更できる。
- 現在の参加確定者数より小さい定員には変更できない。
- 定員を増やした場合は、増えた枠の分だけ待機者を position 順に繰り上げる。
- 定員増加で繰り上げが起きた場合、API レスポンスに `WAITLIST_PROMOTED` の警告(繰り上げ人数)を含める。(Phase 5 で決定)

### 参加登録・キャンセル
- 定員に達したイベントには通常の参加登録ができない。(仕様)
- 登録締切を過ぎたイベントには登録できない。(仕様)
- 開催開始済みのイベントには登録できない。(仕様)
- 同一ユーザーの二重登録は、アプリの判定と DB の一意制約の両方で防ぐ。(仕様)
- 主催者は自分のイベントに参加登録・キャンセル待ち登録できない。主催者は参加者とは別管理とし、定員・登録者数・出席率に含めない。理由: 定員の意味を一定にし、出席・フィードバック・集計での除外分岐をなくすため。
- 本人のキャンセルはキャンセル期限前のみ可能。(仕様)
- admin は期限後も他人の参加を強制キャンセルできる。(仕様)
- キャンセルは `registrations` の行を物理削除する。理由: キャンセルは参加履歴ではないため。
- キャンセル後の再登録は可能。
- 参加登録の判定順: イベントの存在 → 主催者でない → 開催開始前かつ登録締切前 → 未登録・未待機 → 空きあり。
- 空き数 = `max(capacity - 参加確定者数, 0)`。

### キャンセル待ち・繰り上げ
- 満席時のみキャンセル待ちに登録できる。空きがある場合は拒否する。
- キャンセル待ちも登録締切前・開催開始前のみ登録できる。
- 待機中のユーザーはいつでも待機解除できる。(仕様)
- position は `そのイベントの現在の待機行の最大 position + 1`(行が無ければ 1)で採番し、待機解除・繰り上げ時に振り直さない。最後尾が抜けた直後は同じ番号が再利用されうるが、残っている全員より後ろになるため順序は崩れない。(Phase 5 で「過去最大 + 1」から修正)理由: 後続を詰める方式は多数行の更新と一意制約の衝突が起きるため。
- 画面に表示する待機順位は、position 昇順で数えた順位を API が計算して返す。
- 待機を解除して再登録した場合は最後尾になる。
- 参加登録・キャンセル・待機登録・待機解除・定員変更は、トランザクション内で最初に `SELECT ... FOR UPDATE` でイベント行をロックし、イベント単位で直列化する。
- 一意制約違反(Prisma `P2002`)は `409 ALREADY_REGISTERED` に変換する。
- キャンセル時は 1 トランザクションで、参加確定行の削除 → 先頭待機者の参加確定への昇格 → 待機行の削除 → 繰り上げ履歴の記録 を行う。(仕様)
- 繰り上げは開催開始前なら登録締切後でも行う。開催開始後のキャンセルでは繰り上げない。
- 繰り上げ履歴には、イベント、繰り上がった人、空きを作った人(定員増加時は NULL)、きっかけ、繰り上げ時点の position、日時を記録する。履歴は追記のみ。(仕様)

### カテゴリ・タグ
- 初期カテゴリは 勉強会 / 懇親会 / 講演会 / 研修 / その他。(仕様)
- カテゴリ名は一意で、大文字小文字違いの重複も拒否する。カテゴリ名は 1〜30 文字。
- イベント(論理削除済みを含む)が紐づくカテゴリは削除できない。紐づくイベントがなければ物理削除する。
- 使用中のカテゴリは `isActive: false` で無効化できる。無効カテゴリは新規選択肢と一覧の絞り込み候補から消え、既存イベントの表示には残る。
- カテゴリ削除方針の理由: 別カテゴリへの自動移動は主催者の意図しない分類変更と過去集計の書き換えになり、論理削除のみだと未使用の誤登録カテゴリが残り続けるため。
- タグは `trim` → NFKC 正規化 → 英字の小文字化 → 連続空白を 1 つに、の順で正規化して保存・検索する。
- タグは 1〜20 文字。正規化後に重複したタグは 1 つにまとめる。
- 未登録のタグはイベント保存時に作成する。使われなくなったタグは削除しない。
- タグ検索は正規化後の完全一致。

### 出席
- 出席マークは開催開始日時以降のみ可能。それ以前はバリデーションエラー。(仕様)
- 出席状態は `UNMARKED` / `PRESENT` / `ABSENT` で、マーク後も相互に変更できる(未マークに戻すことも可能)。(仕様: 変更可)
- 出席率 = 出席回数 ÷ (出席回数 + 欠席回数)。未マークは分母から除外する。(仕様) 分母が 0 の場合は `null`。
- 累計参加数 = 開催開始済み・未削除のイベントのうち、参加確定で `ABSENT` 以外(`PRESENT` + `UNMARKED`)の件数。
- カテゴリ別参加傾向は、累計参加数と同じ母集団をカテゴリ別に件数集計する(無効化カテゴリも含む)。

### フィードバック
- 投稿できるのは、イベントが未削除、開催終了済み(`now >= ends_at`)、自分の参加が `PRESENT`、自分が主催者でない、未投稿、のすべてを満たす場合のみ。(仕様)
- 評価は 1〜5、コメントは 1〜200 文字。
- 1 イベントにつき 1 人 1 件。2 件目は不可、本人による編集は可能。(仕様)
- 編集時も出席状態が `PRESENT` であることを再確認する。
- 出席が後から変更されても、既存のフィードバックは削除しない。
- 匿名投稿の投稿者は一般ユーザーには表示せず、admin には表示する。(仕様)
- 非公開化されたレビューは、平均評価・件数の集計と一般ユーザーの一覧から除外する。(仕様)
- 非公開化されたレビューは、投稿者本人には「非公開」状態で見える。admin には「非公開」ラベル付きで一覧に表示する。
- 平均評価は小数第 1 位に丸める。0 件なら `null`。
- admin は非公開化したレビューを再公開できる。
- 非公開化されたレビューを投稿者が編集しても、非公開状態は変わらない(admin の判断を投稿者が解除できないようにするため)。(Phase 5 で決定)

## 5. API設計方針

- REST API。ベースパスは `/api`、JSON のみ。
- 成功レスポンスは `{ data }`。作成は 201、削除・解除は 204(ボディなし)、それ以外は 200。
- 失敗レスポンスは `{ error: { code, message, details? } }`。`details` は `{ field, message }[]`。
- エラーコードとステータスの対応は `shared/src/api.ts` の `ERROR_STATUS` にのみ定義する。
- 入力形式の不正は 400、ビジネスルール違反の状態エラー(満席・締切後など)は主に 409 を返す。
- 開催前の出席マークは 400 `EVENT_NOT_STARTED`、主催者の自己登録は 403 `ORGANIZER_CANNOT_REGISTER`、投稿条件不足は 403 `FEEDBACK_NOT_ALLOWED`。
- テンプレートの `EMAIL_TAKEN` は削除する。
- 日時は ISO 8601 UTC 文字列(`Z` 付き)でやり取りする。
- パスパラメータも Zod で検証する。
- リソース名は複数形。ログインユーザー自身の 1 件は単数形のサブリソース(`/registration`, `/waitlist`, `/feedback`)で表し、URL にユーザー ID を入れない。
- 参加登録とキャンセル待ち登録は別エンドポイントにする。
- admin 専用操作も `/admin` 配下にまとめず、通常のリソースに置いて権限で制御する。
- 一覧のページングは `page`(1 始まり, 既定 1)と `limit`(既定 20, 最大 50)。レスポンスは `{ items, total, page, limit }`。
- イベント一覧はデフォルトで開催前のイベントのみ、開催日昇順。`includePast` で開催済みも含める。ソートは `startsAt_asc` / `startsAt_desc`。
- キーワード検索はタイトル・説明文の部分一致(大文字小文字無視)。(仕様)
- イベント一覧を存在しない `categoryId` で絞り込んだ場合は、エラーにせず 0 件を返す。(Phase 5 で決定)
- カテゴリ一覧の `includeInactive=true` は admin のみ有効。admin 以外が指定した場合はエラーにせず無視する。(Phase 5 で決定)
- イベント詳細 API はボタン制御用の `permissions` を返す。サーバー側でも必ず再判定する。
- 匿名レビューの投稿者は、同じ API で閲覧者のロールによって出し分ける。
- エンドポイント一覧は `docs/manifest.md` 5-4 の 26 本(A1〜A3, E1〜E5, R1〜R5, W1〜W2, F1〜F4, C1〜C4, T1, M1〜M2, H1)。

## 6. 通知

- 通知の実送信(メール・Slack など)は行わず、ログ出力で代替する。(仕様)
- ログ出力の対象は、キャンセル待ちの繰り上げ、参加者がいる状態での開催日時の変更、参加者・待機者がいるイベントの削除。
- 通知のログ出力はトランザクションのコミット後に行う。ロールバックされた処理のログは出さない。
- admin の強制キャンセルそのものはログ出力しない(それに伴う繰り上げのみ出力する)。(Phase 5 で決定)
- 将来の通知用の記録は、繰り上げ履歴(`waitlist_promotions`)のみ残す。
- アプリ内通知は、開催日時変更時に参加確定者向けのバナーをイベント詳細に表示するのみとする。

## 7. 画面構成・UI/UX

- 画面は個別ページで構成する: ログイン、イベント一覧、イベント詳細、イベント作成、イベント編集、出席管理、フィードバック投稿・編集、マイページ、カテゴリ管理(admin)、404。
- `/` はイベント一覧にリダイレクトする。
- 参加ボタンは 1 つのボタンを状態で切り替える: 主催者(ボタンなし)/ 受付終了 / 参加登録 / キャンセル待ちに登録 / キャンセル / キャンセル期限切れ / 待機中(順位表示 + 待機解除)。
- 参加のキャンセルには確認ダイアログを出す。
- 参加確定者がいる状態で日時を変更する場合、保存前に確認ダイアログを出す。
- 日時変更の警告は、保存後にトーストでも主催者に知らせる。
- 日時入力はネイティブの `datetime-local` を使い、JST として扱って UTC に変換して送る。変換は `frontend/src/utils/datetime.ts` に集約する。
- 画面の日時は JST(`Asia/Tokyo`)で表示する。
- ボタンの表示制御は API の `permissions` に従い、フロントで権限ロジックを再実装しない。
- 権限のないページに直接アクセスした場合は「権限がありません」画面を表示する。admin 専用ルートはルートガードでも弾く。
- 409 系エラーを受けたらメッセージを表示し、詳細を再取得する。
- イベント一覧はカードのグリッド表示とし、スマートフォン幅では 1 列にする。
- 一覧のカードには、タイトル・カテゴリ・タグ・開催日時・主催者名・定員・登録者数・空き数・自分の状態を表示する。
- タグ検索は、既存タグを候補表示するオートコンプリート入力(`GET /api/tags`)とし、カード上のタグをクリックするとそのタグで絞り込む。
- マイページの統計は、累計参加数と出席率を数値で、カテゴリ別参加傾向を Tailwind の横棒で表示する。グラフライブラリは使わない。
- 主催者は詳細画面で参加者リストとは別に表示する。
- フロントの feature 構成: `auth`, `events`, `registrations`, `feedbacks`, `categories`, `me`。

## 8. インフラ・開発環境・コード管理

- Prisma スキーマとマイグレーションはテンプレートの位置 `backend/prisma/` に置く(仕様の `prisma/schema.prisma` はこの位置を指すものとし、manifest と README に明記する)。
- ブランチは `main` のみに直接コミットする。
- コミットメッセージは Conventional Commits(`feat(scope): ...` / `fix` / `docs` / `test` / `refactor` / `chore`)にする。
- CI は GitHub Actions で、push 時に lint・型チェック・バックエンド API テスト(Postgres サービスコンテナ使用)・フロントエンドテストを実行する。E2E テストは CI では実行せずローカルで実行する。
- `docker compose up -d` だけで `db` / `backend` / `frontend` が起動する。(仕様)
- `db` は `postgres:17`(ホストポート 5433)でヘルスチェック付き。初回起動時に `app_test` DB も作成する。
- `backend` は `node:24`(ポート 3000)。`db` が healthy になってから `prisma migrate deploy` → `seed` → `tsx watch` の順に実行する。
- `frontend` は `node:24`(ポート 5173)で `vite --host 0.0.0.0`。`/api` は `API_PROXY_TARGET`(Docker では `http://backend:3000`、既定 `http://localhost:3000`)へプロキシする。
- ソースはボリュームマウントしてホットリロードを有効にする。`node_modules` は名前付きボリュームにしてホストと共有しない。
- コンテナは `TZ=UTC` で動かす。
- backend の環境変数は compose の `environment` で開発用の値を渡す。本物の秘密情報は置かない。
- `npm run db:up` は `db` サービスのみ起動するよう変更する。ローカル実行(`npm run dev`)も引き続き可能とする。
- seed は何度実行しても同じ状態になるようにし、日時は実行時刻からの相対値で作る。
- seed ユーザー: `admin@example.com`(ADMIN)、`alice` / `bob` / `carol` / `dave` / `erin`(`@example.com`, MEMBER)。パスワードはすべて `password123`(開発専用)。
- seed イベントは、空きあり・満席 + 待機 2 名・登録締切済み・キャンセル期限済み・開催済み(出席状態混在 + レビュー 3 件)・フィードバック未投稿の出席者あり・論理削除済み・無効化カテゴリ使用、の各パターンを用意する。
- テンプレートの `todos` 関連とサインアップは削除する。
- E2E テストは `e2e/` ワークスペースに置く。
- 動作確認のスクリーンショットは `docs/screenshots/` に保存する。
