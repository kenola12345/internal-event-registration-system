# 技術スタック提案

> 入力: `docs/初期選定要素リスト.md`、課題仕様書。Manifest Phase 2 の成果物。

## 前提条件の整理

**前提条件**(課題仕様書から)
- 利用者は社内の社員のみで、規模は小さい。member / admin の 2 ロールで、主催者はイベントごとの権限。
- 一般的な Web アプリの SPA。凝った UI は不要で、機能が正しく動くことを最優先する。
- モバイル対応とアクセシビリティ対応は任意。
- 実働は約 2 日(13〜19 時間)。新しさより安定性、AI での生成精度、資料の多さを優先する。
- リアルタイム通知は不要で、通知はログ出力で済ませる。

**確定事項**(議論しない)
- 言語・フレームワークは TypeScript / React / Express / Prisma / PostgreSQL。
- JWT 認証で、トークンにロールを入れる。パスワードは bcrypt でハッシュ化する。
- `docker compose up -d` だけで DB・backend・frontend が起動する。
- DB は UTC で保存し、画面は JST で表示する。
- E2E テストを書く場合は Playwright を使う。
- 既存テンプレート(npm workspaces のモノレポ)を土台にする。

## 推奨技術スタック(概要)

| レイヤー | 推奨技術 | 主なライブラリ・ツール |
|---|---|---|
| フロントエンド | React 19.3 + Vite 8(SPA) | React Router 8(ライブラリモード)、TanStack Query 5、Tailwind CSS 4.3、Zod 4.6(`shared/` の共有スキーマ)、date-fns 4 + date-fns-tz 3 |
| バックエンド | Node.js 24 + Express 5.3(ESM, TypeScript) | Zod 4.6、Prisma 7.10(`@prisma/adapter-pg`)、jsonwebtoken 9、bcrypt 6、cookie-parser、helmet、express-rate-limit、既存の JSON Lines ロガー(`lib/logger.ts`) |
| データベース | PostgreSQL 17(Docker) | Prisma Migrate、`timestamptz`、CHECK 制約、`SELECT ... FOR UPDATE` |
| テスト(ユニット / E2E) | Vitest 5 + Playwright | Supertest 7(API・実 DB)、Testing Library 16(コンポーネント)、`@playwright/test`(E2E, Chromium のみ) |

## 選定理由

### フロントエンド
- **SPA(Vite + React Router のライブラリモード)**: 全ページがログイン必須の社内ツールなので、SEO も初回表示の速さも不要。SSR(Next.js など)を入れると、Cookie 認証やサーバー/クライアント境界の設計が増えるだけで、2 日の工数に見合わない。
- **TanStack Query**: 空き数、待機順位、平均評価といった「サーバーが正しい値」の表示が中心。登録やキャンセルのあとに関係するクエリを無効化(invalidate)すれば、一覧・詳細・マイページがまとめて最新になる。リアルタイム通信は不要と判断したので、表示時の取得と操作後の再取得で足りる。
- **Zod スキーマを `shared/` で共有**: 「過去日時は禁止」「締切は開催日時以前」のように前後関係を見るバリデーションが多い。フロントとバックで同じ定義を使えば、ルールのずれが起きない。
- **Tailwind CSS**: 凝った UI は求められていないので、コンポーネントライブラリは入れない。テンプレートのデザイントークンで十分。
- **date-fns-tz**: 「UTC で保存し JST で表示」に加えて、`datetime-local` の入力値を JST として UTC に変換する処理が要る。`Intl` だけで逆方向の変換を書くと間違えやすいので、変換は専用ライブラリに任せる。
- 共通: いずれも広く使われていて資料が多く、AI が正確なコードを生成しやすい組み合わせ。

### バックエンド
- **Express 5**: 非同期ハンドラで発生した例外を自動でエラーハンドラに渡すので、コントローラに try/catch を書かずに済み、「想定外の 500 を出さない」という要件を 1 か所の処理で守れる。
- **Prisma 7 の対話的トランザクションと `$queryRaw`**: キャンセル待ちの繰り上げは「行ロック → 削除 → 昇格 → 履歴の書き込み」を 1 トランザクションで行う必要がある。`$transaction(async (tx) => …)` の中で、タグ付きテンプレートの `$queryRaw` を使って `FOR UPDATE` を発行できる。パラメータ化されるので SQL インジェクション対策にもなる。
- **jsonwebtoken + httpOnly Cookie**: ロール入りの JWT をスクリプトから読めない場所に置くことで、レビューコメントのような自由入力が XSS に悪用されても、トークンは盗まれない。cookie-parser で読み取る。
- **express-rate-limit / helmet**: ログインの総当たり対策と基本的なセキュリティヘッダを、少ないコードで入れられる。
- **既存の JSON Lines ロガー**: 「通知はログ出力」の要件(繰り上げ・日時変更・削除)を構造化された形で残せる。依存ライブラリも増えない。
- **Node.js 24**: テンプレートの `.nvmrc` と同じにし、Docker イメージは `node:24` を使う。

### データベース
- **PostgreSQL 17**: 次の 4 つが標準機能で揃う。
  - `timestamptz`: UTC での保存を DB が保証する。
  - CHECK 制約: 定員、評価 1〜5、日時の前後関係を DB 側でも守る。
  - 行ロック(`FOR UPDATE`): 同時キャンセル時の繰り上げを直列化する。
  - 部分一致検索: `ILIKE`(Prisma の `mode: "insensitive"`)で行える。
- 社内規模ならキーワード検索に全文検索エンジンや pg_trgm は不要で、インデックスは日付・カテゴリ・タグの中間テーブルに張れば十分。

### テスト
- **Vitest(バックエンドとフロント共通)**: バックエンドとフロントを同じテストランナーで書ける。Vite の設定(`@/*` エイリアスなど)もそのまま使える。
- **Supertest + 実 DB(`app_test`)**: 繰り上げのトランザクション、一意制約、CHECK 制約は、Prisma をモックすると検証できない。同時キャンセルを `Promise.all` で再現するテストを、本物の PostgreSQL に対して実行する。
- **Playwright**: 仕様書の指定。Docker で起動した環境(`localhost:5173`)に対して実行し、「満席 → 待機 → キャンセルで繰り上げ」のような複数ユーザーのシナリオは、ブラウザコンテキストを分けて再現する。対象ブラウザは Chromium だけに絞り、実行時間を抑える。動作確認のスクリーンショットや動画もここで取れる。

## 確定事項の実現方法

**モノレポ**: npm workspaces を使う(テンプレートのまま)。

```
/
├── shared/      Zod スキーマ・API 型・エラーコード(@template/shared)
├── backend/     Express + Prisma(prisma/schema.prisma, migrations, seed.ts)
├── frontend/    React SPA
├── e2e/         Playwright(ワークスペースとして追加)
├── docker/      postgres-init(テスト DB 作成)
├── docs/        manifest.md, coding_standards.md など
└── docker-compose.yml
```

**`docker compose up -d` だけで全部が起動する構成**

| サービス | 起動内容 |
|---|---|
| `db` | `postgres:17`、ヘルスチェック付き |
| `backend` | `node:24`。`db` が healthy になるのを待ってから `prisma migrate deploy` → `seed` → `tsx watch` |
| `frontend` | `node:24`。`vite --host 0.0.0.0`。`/api` へのリクエストは `API_PROXY_TARGET=http://backend:3000` にプロキシする |

- ソースコードはボリュームマウントしてホットリロードを効かせる。`node_modules` は名前付きボリュームにして、ホストとは共有しない。

**タイムゾーン(UTC 保存 / JST 表示)**

| 層 | 設定 |
|---|---|
| DB | すべての日時カラムを `@db.Timestamptz(3)` にする。DB とコンテナの TZ は UTC のまま(変更しない) |
| バックエンド | コンテナを `TZ=UTC` で動かし、日時の比較は常に `new Date()`(サーバー時刻)で行う。API は ISO 8601(`Z` 付き)で返す |
| フロントエンド | `utils/datetime.ts` だけで `date-fns-tz` を使い、表示は `Asia/Tokyo`、`datetime-local` の入力値は JST → UTC に変換する。ブラウザの TZ には依存しない |

**JWT とロール**: ペイロードは `{ sub, role }` だけにし、署名アルゴリズムは HS256 に固定する。主催者権限はトークンに入れず、リクエストごとに DB で判定する。

## 初期選定要素リスト「1.」への回答

| 問い | 回答 |
|---|---|
| SPA か SSR か | Vite + React の SPA。React Router はライブラリモードで使う |
| サーバー状態の管理 | TanStack Query |
| バリデーションの共有 | `shared/` の Zod スキーマをフロントとバックの両方で使う |
| リアルタイム反映 | しない。表示時に取得し、操作後に再取得する。409 エラー(満席など)を受けたら詳細を取り直す(具体的な画面の挙動は Phase 5 の画面設計で決める) |
| 日時ライブラリ | date-fns + date-fns-tz |
| スタイリング | Tailwind CSS のみ。コンポーネントライブラリは使わない |
| テストフレームワーク | Vitest + Supertest + Testing Library + Playwright |

## 検討したが採用しなかった選択肢
- **Next.js**: 全ページがログイン必須で SSR の利点がなく、構成が複雑になるだけ。
- **Day.js**: プラグインを読み込む順番でタイムゾーンの扱いがずれやすい。date-fns の方が型が素直。
- **Jest**: Vite と ESM で設定が二重になる。
- **Testcontainers**: compose の `app_test` DB で十分。CI を高速化したくなった時点で検討する。
